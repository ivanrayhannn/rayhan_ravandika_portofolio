What I owned

Four modules on two platforms. My job was to decide what we built, describe it precisely enough to build, and make sure it shipped working.

  1. Scope and backlog

    Roadmap, PRD and prioritised user stories for each module, agreed with the CTO, VP and product team.

  2. UI design

    Mobile screens for employees and web screens for HR admins and approvers, designed in Figma.

  3. API endpoints

    Endpoint list, request and response bodies, and error cases, written as a JSON API spec with the backend engineers.

  4. Documentation

    Every decision went into the PRD, user stories with acceptance criteria, screen specs and the API spec, so engineering and QA worked from one source.

  5. Delivery

    Sprint planning, reviews and requirement clarification, then QA, UAT and defect prioritisation before each release.

Released features: attendance you can trust

Two features shipped to stop the most common attendance problems: clocking in from somewhere else, and clocking in for someone else. Every button on these screens works: try them.

Released · Attendance module

Geofenced attendance

Problem. Employees could clock in from home or on the way to the office, and HR had no way to tell from the log.

How it works. HR sets each work location on a map with a radius. When an employee taps Clock in, the app reads the phone's location. Inside the radius, the clock-in is saved with the location. Outside it, the app explains how far away they are and what to do next.

  • Location turned off: the app asks to turn it on before clocking in.
  • Weak GPS signal: the app asks to wait a moment and try again.
  • More than one office or site: the employee is checked against every location assigned to them.

Released · Attendance module

Face match at clock-in

Problem. Colleagues clocked in for each other (titip absen), so the log showed people at work who weren't there.

How it works. Each employee has a registered photo approved by HR. At clock-in the app takes a selfie and compares it with that photo. A match saves the clock-in. A face that doesn't match still saves the clock-in, but flags it: the employee sees the flag right after clocking in, the date gets a red border in their own attendance list, and HR reviews it.

  • No face in frame or the room is too dark: the app asks for a new photo before comparing.
  • Face doesn't match: the clock-in is saved with an Unmatched flag, and that date shows a red border in the employee's attendance list until HR accepts or rejects it.
  • Appearance changed, for example glasses or a new haircut: HR can approve a new registered photo.

How each sprint ran

Every module was built in Scrum sprints. This is my part of each one, from preparing the features to checking them in production.

  1. Pre-sprintResearch the features and detail them for backend, frontend and mobile.
  2. PlanningPresent the features to the team, often as acting Scrum Master, then revise and finalise the requirements from their feedback.
  3. SprintWrite the test scenarios with QA while the engineers code, and answer their questions as they come up.
  4. TestingQA tests each feature, and I review the results.
  5. ReviewQA and I present the finished features to the project team.
  6. ReleaseThe infra team deploys the ready features, and QA tests them again in production.

Example user story, overtime module

As an employee, I want to request overtime from my phone before I work it, so my manager approves it in time and the hours count in payroll.

  1. Given I open Overtime, when I send a request with date, planned hours and reason, then my manager gets it in the approval inbox and I see "Waiting".
  2. Given my manager approves, when I open the request, then I see "Approved" and the hours appear in my monthly summary.
  3. Given the planned end time is earlier than the start time, when I tap Send, then the form shows "End time must be after start time" and nothing is sent.

Policy master: each company sets its own rules

Overtime and leave rules differ from one company to the next, so neither module hard-codes them. Each company builds its own policy master on the web, and the mobile app applies it to every request.

Overtime

HR sets an overtime rate for each position. A request is paid at the rate of the employee's position, so payroll gets the right amount without manual checks.
